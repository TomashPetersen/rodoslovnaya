# Подготовка общего коммита и отправки

Это инструкция подготовки исходников и БЗ к GitHub. Датированные результаты находятся в [журнале подготовки](../research-data/knowledge-checks-2026-11-17.json). Перед действием проверить текущее состояние заново: состав файлов и результаты могут измениться.

На проверке подготовки 17 ноября поиск в имитации телефона превысил порог времени в основном прогоне и повторе; полный аудит выявил замечания в средствах разработки. Более поздний [журнал размещения](../research-data/deployment-checks-2026-11-17.json) содержит успешный полный браузерный прогон. Это разные наблюдения, они сохранены без переписывания истории. Для передачи 20 ноября проверки выполнены заново в [журнале передачи](../research-data/github-handoff-2026-11-20.json).

Владелец прямо разрешил новый публичный репозиторий и отправку исходного состава. Цель - совместная разработка через отдельные ветки и PR, запросы на включение изменений. Это разрешение относится к исходникам и проектным документам; семейные архивы и секреты в состав не входят. Известные замечания средств разработки сохраняются как открытый технический долг с оценкой применимости, а не как успешный полный аудит.

Не включать `app/node_modules/`, `app/dist/`, результаты браузерных проверок, `output/`, `research-data/apps/`, `research-data/downloads/`, локальные настройки и секреты. Точные правила находятся в [.gitignore](../.gitignore). Исключение не удаляет файлы с диска. Настоящие семейные данные и копии не должны попадать в Git независимо от расширения.

В начале задачи все материалы были неотслеживаемыми. Поэтому будущий первый коммит будет включать и существующее приложение с исследованием, и нынешнюю доработку БЗ. Он не должен описываться как одна правка ссылок.

## Проверки перед отправкой

Помимо исходного состава, в общий коммит входят корневой `README.md`, инструкция `knowledge/collaboration.md`, настройка `.github/workflows/checks.yml`, материалы размещения `knowledge/hosting.md`, `ops/` и их датированные журналы/разборы. Поименный состав фиксируется в журнале передачи; старый перечень 17 ноября не заменяет эту проверку.

1. Проверить `git status --short`, `git branch --show-current`, `git log -1 --oneline`, `git remote -v`. Если история отсутствует, это ожидаемое состояние только до первого коммита. Не подставлять предполагаемый адрес GitHub.
2. Из корня выполнить `node scripts/check-knowledge.mjs --self-test` и `node scripts/check-knowledge.mjs`.
3. Из `app/` выполнить весь [набор проверок](../app/README.md#проверки-и-границы-поддержки), включая сборку перед браузером. Затем выполнить `npm.cmd audit` для всех зависимостей. Не запускать автоматическое обновление ради скрытия замечаний; зафиксировать затронутые пакеты и решение отдельно.
4. Проверить точный будущий состав: `git ls-files --others --exclude-standard`, `git diff --check`, а после разрешенного добавления файлов - `git diff --cached --check`, `git diff --cached --stat` и содержимое подготовленных изменений. До первого коммита пустой `git diff` не означает отсутствие файлов: основные материалы еще не отслеживаются.
5. Вручную проверить новые материалы на секреты, семейные сведения и сторонние исполняемые файлы. Просмотреть снимки. Выполнить отдельную языковую вычитку измененных Markdown-файлов и обновить датированный журнал подготовки.

Незавершенная приемка телефонов остается явным ограничением продукта. Она не запрещает хранение проверенных исходников в репозитории, но не позволяет назвать приложение принятым на этих устройствах. Ошибки обязательных технических проверок нужно устранить или явно разрешить отдельным решением до отправки.

## Внешнее действие

Просьба подготовить коммит и отправку не выполняет их автоматически. Нужны прямая команда на `commit`/`push` и точный удаленный репозиторий. Создание репозитория и его публичность также не выбираются молча. Добавлять только проверенные пути поименно, без `git add .` и `git add -A`.

Рекомендуемое содержание сообщения первого общего коммита: «Добавить локальное приложение Родословная, исследование и базу знаний». Фактическое сообщение должно соответствовать окончательному составу. Отправка в GitHub не является публикацией приложения и не разрешает загрузку семейных данных.

Для порученной передачи используется [публичный репозиторий](https://github.com/TomashPetersen/rodoslovnaya), основная ветка `main`. После первоначального наполнения изменения передаются по [порядку совместной работы](collaboration.md). Правила ветки на GitHub и результаты автоматических проверок проверяются отдельно от наличия файла настройки.

В автоматических проверках полный аудит сохраняет исходный результат. Отдельный обязательный шаг разрешает только два известных бюллетеня из датированной оценки: новые или поврежденные сведения, ошибки получения отчета и высокие/критические уязвимости блокируют проверку. Аудит рабочих зависимостей остается обязательным без исключений. Изменение инструментов, шаблонов или источников путей требует пересмотра оценки применимости прежних замечаний.
